# Bounded operation and measurement

Run `docker compose up --build -d --scale api=2 --scale worker=2` with one Redis admission authority. Nginx resolves the API service's replica addresses and balances connections. Disable proxy retries: a lost purchase response may have allocated stock. Retry the same request key or look up the identifier. Workers independently claim the shared `orders` consumer group; PostgreSQL uniqueness remains the final duplicate guard. No global or distributed ordering guarantee is made beyond the single Redis script execution order.

Each API has HTTP_CONCURRENCY=64 concurrent handlers with no application waiting queue. Excess requests return 429 busy and Retry-After: 1 before route work. ADMISSION_CONCURRENCY=16 independently limits durability sockets with no wait queue; exhaustion before send is busy. ADMISSION_TIMEOUT_MS=3000 bounds those sockets; failures after possible send remain PROCESSING/confirming. Client disconnects do not cancel admission or release stock. DATABASE_POOL_SIZE=10 bounds connections, and DEPENDENCY_TIMEOUT_MS=2000 bounds pool acquisition and queries. HTTP admission bounds API database waiters. Workers process sequentially with read/claim batches of ten and bounded retry metadata. Redis connections disable offline buffering and cap command queues at 256. No per-identifier throttles apply. Body and URL limits remain documented in the public contract.

Nginx bounds body/header/send inactivity to five seconds, connect to two seconds and upstream read to five seconds. Compose caps each API/worker at one CPU and 512 MiB; proxy at half CPU and 64 MiB. These are protective infrastructure limits, not demonstrated burst capacity. Redis retains AOF everysec, noeviction and local WAITAOF confirmation under load. Stream data is retained for recovery; Redis storage grows with admitted work, so provision persistent storage for the sale and retained evidence.

Scrape each replica's `/metrics` directly (API also through `/api/metrics` for inspection). Scraping only the proxy samples one replica and cannot aggregate fleet counters. Metrics reset on restart. Names have no user/request/sale labels. Counters cover HTTP requests/errors/busy, purchase response outcomes by fixed reason (admitted, uncertain, busy and business rejections), worker attempts/retries and database completions. Purchase counters count deliveries, including replays, not distinct allocations. Purchase outcomes describe the final response; uncertain admissions may be resolved by subsequent order lookup. Database completion counts successful processing attempts, including safe replays. Barrier and HTTP latency expose seconds sum/count; resource gauges expose RSS, used heap, cumulative CPU and database pool connections/waiters. Shared stream backlog is stream length minus completion mappings; pending is the consumer-group pending count and delayed is retry-due cardinality. Shared gauges must not be summed across replicas. `metrics_sample_available=0` means the dependency gauges are stale. Metrics access is infrastructure access; do not expose it publicly without appropriate network controls.

Purchase logs correlate hashed request keys and sale/identifier reservation keys. Worker logs use the same hashes and include the committed order UUID. Raw identifiers and URLs are omitted. Hashes provide correlation, not anonymization of low-entropy values.

For every repeatable run save `docker compose config` securely (it includes credentials), `docker compose ps`, replica counts, image/commit IDs, host CPU/RAM, all limit overrides, sale configuration, generator dispatch interval and metrics from every replica before/after/drain. Record `docker stats --no-stream` and periodic RSS/heap samples during sustained overload and recovery. The DEV-19 experiment stage supplies measured long-run memory and capacity evidence; unit overload checks verify bounded handler occupancy, not a production memory ceiling.
